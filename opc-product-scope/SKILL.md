# OPC 产品范围取舍

个人开发者的开发与维护能力有限。优先完成最关键的用户任务，而不是补齐同类产品的功能表。AI 能更快写代码，只降低部分实现成本，不能证明功能值得做。

## 触发与介入力度

- 新功能或明显扩大产品范围的改动：先做简短取舍，再进入需求澄清或实现。
- 明确的小幅体验调整：检查它是否引入新的范围或维护负担；没有则简述最小范围并继续，不重新问诊。
- 用户已明确决定要做：沿用决定，重点收敛实现范围、必要质量和验证方法，不反复劝退。发现新的具体风险或矛盾时说明影响。
- 明确故障修复、纯实现问题、机械修改：进入相应工作流程。修复过程中另提出的功能扩张，单独评估。
- 产品取舍与营销取舍是不同场景；仅在问题确实同时涉及二者时分别处理，共用已知背景与总资源预算。

评估服务于原请求，不增加固定的确认关卡。信息足够且实施已获授权时，给出简短结论后继续必要工作；未决定的产品取舍、真实阻断或会改变方案的必要信息才询问用户。

## 1. 锚定核心用户任务

沿用会话、项目文档及真实反馈，写清：**谁，在什么场景下，要完成什么结果，现在被什么阻碍？** 再确定完成结果所需的最短路径。实现事实由 agent 核查，不把可查的信息交给用户猜。

需求含糊且会改变取舍时，优先问最关键的 1～2 个问题；其余未知项标为假设。用户任务与已有项目决定冲突时，说明冲突，请用户作产品决定，避免自行改掉原定目标。

## 2. 评估候选改动

用下列问题形成判断，不强制展示打分或让用户逐项填表：

| 判断项 | 要解决的问题 |
|---|---|
| 痛点证据 | 来自真实行为、反复反馈、明确需求还是猜测？影响谁、发生多频繁、后果多严重？单个严重问题也可能值得优先处理。 |
| 核心关联 | 不做它，用户还能顺利完成核心任务吗？它是在解除阻碍，还是引入另一个任务或人群？ |
| 更小方案 | 文案、现有能力、系统能力、人工处理或小原型能否先解决问题、验证价值？ |
| 全生命周期成本 | 实现、验证、跨端适配、服务依赖、持续维护和支持需要多少投入？有哪些数据迁移或难撤回的决定？ |
| 验证方法 | 哪个可观察的用户行为或质量结果能说明改动有效？何时观察，结果不成立怎么办？ |

**必要质量属于必要范围。** 可靠性、数据安全、无障碍与平台约束有具体依据时，即使不增加可见功能也应纳入；说明依据和最小范围，避免以“基础建设”为由无限扩张。

跨市场或跨平台计划已知时，考虑复用与新增适配成本；未来计划未知时，明确假设，不为假想需求提前搭建系统。

## 3. 做减法并选择验证方式

对实际候选项给出以下决定；已有明确决定的项目只需补齐最小范围：

- **现在做**：解除核心任务的具体阻碍，或满足必要质量与约束。
- **先验证**：可能重要但证据不足，写出最便宜的验证办法和投入上限。
- **暂缓**：有价值但当前收益不足以抵消投入，写明重新考虑的条件。
- **不做 / 考虑移除**：偏离核心任务，或长期负担超过价值；已有功能先核查使用、依赖及用户数据影响，取舍建议不等于删除授权。

证据不足不一律禁止开发：低成本、易撤回的改动可以作为小步验证；长期维护、新服务依赖、数据迁移或大量跨端开发，优先用访谈、原型、现有流程等更便宜的办法验证关键假设。验证先回答一个具体问题，达到结束条件后再决定是否扩大。

## 4. 收敛本轮范围与投入

每轮聚焦一个最影响用户结果的问题；完成同一结果所必需的多个改动可以一起做。

- 写明最小实现范围与明确不包含的衍生功能，避免顺手扩展。
- 沿用已知时间预算；没有就给粗略成本区间与不确定性，仅当预算缺口会改变取舍时再问。估算包含实现、验证及后续维护，不能用 AI 写代码时间代替总成本。
- 较大的工作先划出可独立验证的一小步；必要依赖一并交代，避免交付不可用的碎片。
- 若同时安排开发、推广和用户交流，共用总时间预算，避免分别安排满额。
- 给出完成条件、与改动相称的必要验证、复查时间和继续 / 调整 / 停止标准。无需为低影响改动制造复杂指标或测量工程；数据少时结合实际使用与定性反馈，不制造统计确定性。

## 输出与交接

按复杂度缩放输出。小调整用几句话即可；复杂取舍用一页：

1. 核心用户任务、证据与未知项。
2. 本轮重点及理由。
3. 现在做 / 先验证 / 暂缓 / 不做的实际候选项。
4. 最小范围、明确不包含的内容、投入与维护成本。
5. 完成条件、必要验证与复查标准。

没有实际候选项的类别可以省略。证据和成本不足时标记未知，不编造反馈、工时或成效。

取舍完成后，将最小范围和完成条件交给当前环境可用的需求澄清、原型或实现流程；已授权的实施继续推进，不强制调用不存在的技能，不把本 skill 扩成编码教程。
